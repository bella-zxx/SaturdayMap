# 小红书链接解析基线测试

## Case 01：巨富长半日逛吃

- **测试日期：** 2026-10-20
- **用户提供的分享链接：** https://xhslink.cn/o/2HAggjcl6B9
- **目标笔记 ID：** `6a66b866000000000101f0b1`
- **方法：** 使用 `probe.py` 对公开网页进行 5 次只读请求，不登录，也不绕过访问控制。

| 结果 | 次数 | 观察 |
|---|---:|---|
| 进入笔记页 | 1 | 短链成功跳转；页面标题与目标笔记一致。尚未验证完整正文和图片列表。 |
| 进入登录页 | 4 | 最终地址为 `/login`；没有取得笔记正文。 |

五次请求的 HTTP 状态码均为 200，因此状态码本身不能代表解析成功。登录页中的站点图片和嵌入状态也不能算作笔记图片或正文。

### 阶段结论

短链展开已验证，但仅靠无登录的公开网页请求，当前样本未达到稳定获取正文和图片的 P0 要求。尚不能认定直接网页解析方案可用；也不能根据一个样本推断所有小红书笔记的行为。

### 下一步

1. 对能进入笔记页的响应验证正文完整性和图片列表，而非仅凭页面标题或字段名判断。
2. 评估有明确接口、权限与费用说明的候选服务，记录成功率、数据完整度和失败原因。

## 三个样本的合并观察

| 指标 | 结果 |
|---|---:|
| 短链可展开 | 3/3 篇 |
| 进入笔记页 | 1/11 次请求 |
| 进入登录页 | 10/11 次请求 |
| 已验证完整正文与图片 | 0/3 篇 |

这仅是三个样本的基线测试，不代表整个平台的成功率。当前不能把公开网页直读作为 MVP 的可靠内容获取方案；第三方服务和其他合规接入方式尚未实测。

## 不使用第三方服务的补充检查

对三篇笔记分别直接访问公开网页的 `/explore/{note_id}` 和 `/discovery/item/{note_id}` 两种地址，共 6 次。六次最终都进入 `/404`，页面提示当前笔记暂时无法浏览（错误码 `300031`）；HTTP 状态码仍为 200。未取得正文或图片。这项检查不改变上述 11 次分享链接请求的统计口径。

[小红书开放平台的权限文档](https://openaccount.xiaohongshu.com/docs/scope)显示目前开放的是 `basic_info`；`read_notes` 尚在规划中，且描述为读取授权用户发布的笔记。因此，当前公开文档未提供读取用户粘贴的任意笔记内容的接口。

在“用户只粘贴链接”的既定要求下，公开网页直读和上述官方开放接口目前都无法完成端到端验证。使用用户已登录的浏览器、浏览器扩展或分享扩展可能成为个人原型路径，但会引入额外登录或交互；这些方案尚未测试，也不能直接视为 MVP 解法。

## 完全不登录、也不使用第三方额度的路线复核

按“任何账号都不登录”的约束，复核了公开网页、官方接口和开源工具（2026-10-20）：

| 路线 | 证据与限制 | 当前判断 |
|---|---|---|
| 公开网页直读 | 上述三篇短链 11 次请求中 10 次进入登录页，1 次仅确认标题；六个直接笔记地址均不可浏览 | 可展开短链，未验证正文和图片；不能作为稳定的内容获取方案 |
| 官方开放接口 | [授权范围](https://openaccount.xiaohongshu.com/docs/scope)目前仅开放 `basic_info`，`read_notes` 仍在规划中，且面向授权用户发布的笔记 | 不满足任意分享笔记的读取需求 |
| MediaCrawler | [小红书实现](https://github.com/NanmiCoder/MediaCrawler/blob/main/media_platform/xhs/core.py)在未通过登录状态检测时进入登录流程 | 免费开源不等于无需登录 |
| RSSHub 小红书路由 | [路由实现](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/xiaohongshu/user.ts)使用 Cookie 提取全文；[维护者说明](https://github.com/diygod/rsshub/issues/13497)完整笔记及图片需要配置 Cookie | 无 Cookie 方式不能满足全文与图片要求，且该路由按用户而非任意分享链接工作 |

因此，目前**没有通过验证的“仅粘贴链接、完全不登录、零第三方额度、稳定获得完整笔记”方案**。这不是证明所有未来方案都不可能，而是这轮证据不足以让 MVP 依赖无账号解析。搜索摘要或分享文案只能作为不完整信息，不能冒充原帖正文，更不能让 AI 凭空补足地点。产品“用户只粘贴链接”的需求仍保持不变；内容获取在该约束下标记为技术阻塞。

## 待实测的下一条路线

[TikHub 的小红书 App V2 使用指南](https://blog.tikhub.io/zh/article/7)列出图文笔记详情接口，并说明可直接传分享链接 `share_text`，返回标题、正文和图片等字段。它需要 TikHub 账户及 API Key，调用可能消耗账户额度。这个描述来自服务方文档，**目前没有用上述三篇笔记实测**，不构成方案通过结论。

实测时应复用这三篇样本，逐项核对：正文是否完整、图片是否可读、主要地点是否有原文依据、重复调用是否稳定，以及每次调用成本。若进入第三方试用，API Key 只放在本机环境中，不提交到仓库。

## TikHub 第一次实测（Case 01）

- **日期：** 2026-10-20
- **接口：** `/api/v1/xiaohongshu/app_v2/get_image_note_detail`
- **输入：** 用户提供的巨富长分享短链，参数 `share_text`
- **请求次数：** 本地脚本发起 1 次，未自动重试
- **结果：** HTTP 403；响应没有 API `code`，仅有边缘访问拦截提示：`The site owner has blocked access based on your browser's signature.`

该响应不是笔记详情，也不是接口返回的业务错误；无法据此判断分享链接是否可解析、令牌权限是否正确或是否发生计费。下一步先由用户在 TikHub 控制台核对调用次数和余额变化，再考虑服务方支持的官方测试方式。不要在未确认扣费和拦截原因前重试。

用户核对仪表盘后反馈：调用次数和付费余额均未变化。此观察与请求在进入计费接口前被拦截相符，但不能单独证明服务方如何计费。后续候选测试改用 TikHub 官方 Python SDK，关闭自动重试，并仍只测试 Case 01 一次。
